# Requirements

**University Helpdesk API** — *Sistem për raportimin e problemeve teknike në universitet*

This document describes what the system must do. The design is in
[`design.md`](design.md) and the HTTP contract is in
[`api-contract.md`](api-contract.md).

## Problem and objective

Classroom technology problems, such as a broken projector, a computer that will
not start, or a missing network connection, are often reported informally and
then forgotten. Students do not know whether anyone is working on the problem,
and technicians have no single list of open issues.

The objective is a backend API where:

1. A student signs in and reports a classroom technology issue.
2. A technician sees all reported issues, starts work on them, and marks them
   as resolved.
3. When an issue is resolved, the student who reported it receives a
   confirmation email. During local development, these emails are delivered to
   a Mailpit test inbox instead of real mailboxes.

## Roles

| Role         | Description                                                                 |
| ------------ | --------------------------------------------------------------------------- |
| `Student`    | Reports issues and manages their own tickets while the tickets are still open. |
| `Technician` | Views all tickets and moves them through the status workflow.               |

Each user has exactly one role. There is no self-registration; accounts are
seeded as demo data.

## Functional requirements

**FR-1 Sign-in.** A user signs in with an email and password. On valid
credentials, the API returns a signed JWT that contains the user's ID and role.
Invalid credentials are rejected with a generic error that does not reveal
whether the email exists.

**FR-2 Categories.** Any signed-in user can list the active issue categories.
Every ticket belongs to exactly one active category.

**FR-3 Ticket creation.** A student creates a ticket by giving a room, a
category, and a description. The server sets the owner, the initial status
`Open`, and the timestamps.

**FR-4 Ticket viewing.** A student can list and view only their own tickets. A
technician can list and view all tickets. Lists can be filtered by status and
are paginated.

**FR-5 Ticket editing and deletion.** A student can edit the room, category, or
description of their own ticket, or delete it, only while its status is `Open`.
Technicians cannot edit or delete tickets.

**FR-6 Status changes.** A technician advances a ticket one step through the
workflow `Open → InProgress → Resolved`. Skipping a step, moving backwards, or
changing a resolved ticket is rejected.

**FR-7 Resolution notification.** When a ticket becomes `Resolved`, the system
sends a confirmation email to the student who reported it. Sending is
asynchronous, so a slow or unavailable mail service does not block or fail the
technician's request.

## Data sources

| Data             | Source                                                                 |
| ---------------- | ---------------------------------------------------------------------- |
| Users            | Fictional demo accounts seeded into the database.                      |
| Categories       | Fictional issue categories seeded into the database.                   |
| Tickets          | Created and changed only through API requests.                         |
| Notifications    | Generated by the system when a ticket is resolved.                     |

Demo accounts (all fictional, using the reserved `.test` domain):

| Email                  | Role         |
| ---------------------- | ------------ |
| `student1@uni.test`    | `Student`    |
| `student2@uni.test`    | `Student`    |
| `technician1@uni.test` | `Technician` |

Demo categories: Projector, Computer, Network, Audio, Smart Board, Other.

Demo passwords are development-only values. They are not stored in the
repository: each installation sets its own through configuration
(`DemoAccounts:*`), and the accounts are created only in the Development
environment. They must never be reused outside local development.

Students and technicians use the API through the Swagger UI or an HTTP client
for now; a web frontend is planned but not part of this scope yet.

## Main workflows

**Report an issue.** The student signs in, lists categories, and creates a
ticket. The ticket starts as `Open`.

**Correct or withdraw a report.** While the ticket is `Open`, the student can
edit its room, category, or description, or delete it.

**Resolve an issue.** The technician signs in, lists tickets (optionally only
`Open` ones), moves a ticket to `InProgress`, fixes the problem, and moves it
to `Resolved`.

**Confirm the resolution.** After the ticket is resolved, the Notification
Worker sends a confirmation email to the student, which appears in the Mailpit
inbox during local development.

## Nonfunctional requirements

Each requirement states how it will be verified. Performance figures are
targets; measured results are recorded in `benchmark-results.md`, and the
results of every verification are in `verification-results.md`.

| ID       | Area            | Requirement                                                                                                                                  | Verification                                                                                         |
| -------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| NFR-S1   | Security        | Every endpoint except `POST /auth/login` rejects requests without a valid JWT with `401`.                                                    | Integration tests call each protected endpoint without a token and with an expired or tampered token. |
| NFR-S2   | Security        | Role and ownership rules from the API contract are enforced on the server.                                                                    | Integration tests cover each endpoint with the wrong role (`403`) and another student's ticket (`404`). |
| NFR-S3   | Security        | Passwords are stored only as salted, adaptive hashes. Secrets (JWT signing key, database passwords) come from configuration, not source code. | Code review: accounts are hashed with ASP.NET Core Identity's `PasswordHasher`; integration tests log in against stored hashes; review that no secrets are committed and `.env` files are ignored. |
| NFR-S4   | Security        | Error responses for unexpected failures contain no stack traces or internal details, only a generic message and a trace ID.                  | HTTP test forces an unhandled exception through a test-only route and inspects the response body.    |
| NFR-P1   | Performance     | `GET /tickets` has a p95 latency under 300 ms with 20 concurrent users and 1,000 seeded tickets on the local Docker Compose setup.           | `benchmarks/UniversityHelpdesk.Benchmark` with the documented workload; results in `benchmark-results.md`. |
| NFR-P2   | Performance     | `GET /categories` is served from the Redis cache when it is available.                                                                       | Redis recovery check verifies that the second request is a cache hit and that caching resumes after an outage. |
| NFR-R1   | Reliability     | If Redis is unavailable, `GET /categories` still succeeds by reading from PostgreSQL.                                                         | Unit test with an unreachable Redis, and a recovery check that cuts the Redis connection.            |
| NFR-R2   | Reliability     | A ticket resolution and its pending notification are saved in one transaction; a notification is never lost if RabbitMQ or Mailpit is down. | Recovery check resolves a ticket while the broker is unreachable, then verifies delivery after it returns. |
| NFR-R3   | Reliability     | Concurrent conflicting edits or status changes do not overwrite each other; the losing request receives `409`.                               | Integration test sends two updates with the same version and expects one `200` and one `409`.        |
| NFR-R4   | Reliability     | The API exposes liveness and readiness health checks.                                                                                        | Health checks are called in tests and used by the Compose health checks and Kubernetes probes.       |
| NFR-M1   | Maintainability | Code is separated into HTTP, business logic, and persistence layers as described in the design.                                             | Code review against `design.md`.                                                                     |
| NFR-M2   | Maintainability | Automated tests run in GitHub Actions on every push and pull request, and the build fails on any test failure.                              | `.github/workflows/ci.yml` and its run history.                                                      |
| NFR-M3   | Maintainability | The full local environment starts with a single Docker Compose command.                                                                       | Documented command is run on a clean machine and the health checks pass.                             |
